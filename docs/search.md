# Поиск адресов: пайплайн

Свободная пользовательская строка → разбор → гибридный SQL-поиск по денормализованной
проекции `search.*` → ранжированная выдача. Разбор намеренно «грубый и быстрый»;
окончательное разрешение неоднозначностей делает двухфазное SQL-сужение.

```
строка ──▶ AddressNormalizer.Parse ──▶ ParsedAddressQuery ──▶ AddressSearchRepository ──▶ AddressResult[]
           (нормализация + разбор)      (контейнер/улица/дом)   (FTS + pg_trgm, RRF, сужение)
```

Ключевые типы:
- `Fias.Application/Search/AddressNormalizer.cs` — разбор строки.
- `Fias.Application/Search/ParsedAddressQuery.cs` — результат разбора.
- `Fias.Application/Services/AddressSearchService.cs` — оркестрация + recall-фолбэк.
- `Fias.Infrastructure/Persistence/AddressSearchRepository.cs` — гибридный SQL.

## 1. Нормализация (`AddressNormalizer`)

Класс stateless (статические `FrozenDictionary`/`FrozenSet`), регистрируется синглтоном.

1. **Clean** — один проход по `ReadOnlySpan<char>`: нижний регистр, `ё→е`, остаются
   буквы/цифры/`/`/`-`, всё прочее (включая точки) схлопывается в один пробел. Буфер до
   256 символов — со стека.
2. **TokenizeAndExpand** — разбивка на токены и раскрытие сокращений по словарю
   (`нск→новосибирск`, `спб→санкт-петербург`, `ул→улица`, …). Одно сокращение может
   дать несколько токенов (`нн → нижний новгород`).
3. **SplitTrailingHouse** — с конца отрезаются «домовые» токены (цифра, маркер+цифра
   `к1`, маркеры `д`/`корп`/`стр`). Номер раскладывается на `HouseNum` (база) и
   `Building` (корпус/строение) — они матчятся отдельно против `house_num` и
   `add_num1`/`add_num2`. Если «дом» в самом начале (`д. Ивановка`) — не режем.
4. **SplitContainerAndStreet** — именная часть делится на контейнер (регион/город) и
   улицу. Если есть маркер улицы (`ул`, `пер`, …) — делим по нему; иначе первый токен
   считаем контейнером, остальное — улицей.

Результат — иммутабельный `ParsedAddressQuery` (`RegionOrCity`, `Street`, `HouseNum`,
`Building`, плюс сырые `NameTokens` для фолбэка).

### Инициалы имени улицы

Распространённое сокращение: пользователь пишет `Б.Хмельницкого 2`, имея в виду
`Богдана Хмельницкого 2`. После `Clean` точка превращается в пробел → токены
`б`, `хмельницкого`. Здесь два нюанса:

- **Разбор.** Одиночная буква в начале именной части — это инициал, а не контейнер.
  `SplitContainerAndStreet` не отдаёт её в `RegionOrCity`: вся часть уходит в улицу
  (`Street = "б хмельницкого"`). Иначе `б` ошибочно резолвился бы как «город».
- **Матчинг.** В индексе у «Богдана Хмельницкого» лексемы `богдан` + `хмельницк` —
  литеральной лексемы `б` там нет, поэтому обычный `plainto_tsquery` не сматчил бы.
  Одиночная буква в FTS-терме превращается в **префиксный терм** `б:*`
  (см. §2), который ловит и полное имя (`богдан`), и сам сокращённый вариант в данных
  (`Б.Хмельницкого`), и квалификатор (`Б. Никитская` → `большая`).

Словарь имён не нужен — опираемся на полные названия в данных ГАР.

### Маркеры-омонимы и перечислимые улицы

Часть тип-маркеров в данных ГАР — это и распространённые **имена** улиц: `Набережная`
(321 улица по Челябинску), `Тупик`. Если такой токен стоит последним в именной части
(`Вавиловец Набережная`, `Челябинск Тупик`), это имя улицы, а не тип, — выкидывать нельзя
(`NameLikeMarkers`), иначе поиск находит сам НП. Всё до него — контейнер; если контейнера нет
(`Набережная 5`) — имя уходит в `RegionOrCity` (форма «имя+дом» для многогородного поиска).

Перечислимые маркеры (`квартал`, `кв-л`) несут НОМЕР в имени улицы: в данных то `квартал 4`,
то просто `157` при типе `кв-л`. Отрезанный хвостовой номер тут — часть имени, а не дом
(`EnumerableMarkers`): иначе вырожденный парс отдаёт контейнер в `Street`, слабый trgm-матч на
сам город перебивает recall-фолбэк, и улица не находится. `линия` исключена — `5-я линия 12`
это улица `5-я линия` + дом 12.

Тип-фразы ж/д НП (`Баландино, железнодорожная станция`) — это тип, а не имя: слова
`станция`/`разъезд`/`железнодорожная` в `RegionMarkers` (отбрасываются).

## 2. Гибридный поиск (`AddressSearchRepository`)

Поиск по `search.*` на raw SQL (Dapper). Два независимых сигнала объединяются через
**Reciprocal Rank Fusion (RRF)**:

1. **FTS** — кандидаты ранжируются по `ts_rank(name_tsv, query)`.
2. **pg_trgm** — те же кандидаты по `similarity(name, query)`.

Итог = `Σ 1/(k + rank_i)` по спискам, где кандидат реально совпал (`k = 60`, дефолт
TREC). RRF не требует сводить несравнимые шкалы `ts_rank` и `similarity` к общим весам.
Плюс мягкий бонус уровню (города 4/5 над одноимёнными сёлами) — добавка масштаба одной
позиции RRF, не перебивает качество совпадения. Тай-брейк при равном скоре — по
`house_count` (живая улица с домами выше пустого дубля).

### Построение tsquery

```
@tsqExpr IS NULL  →  plainto_tsquery('russian', @term)          -- обычный случай
@tsqExpr IS NOT NULL  →  to_tsquery('russian', @tsqExpr)         -- есть инициал
```

`BuildPrefixTsQuery` возвращает `null`, если одиночных букв-инициалов в терме нет —
тогда путь побайтово прежний (`plainto_tsquery`), **ноль регрессий**. Если инициал есть,
строит выражение вида `б:* & хмельницкого` (токены чистятся до букв/цифр — вход
`to_tsquery` строго валиден). `to_tsquery` сам прогоняет каждый токен через словарь
`russian` (стемминг), поэтому `хмельницкого → хмельницк`, а `б:*` остаётся префиксом.

## 3. Поуровневое сужение (две/три фазы)

Сужение идёт без единого JOIN — по денормализованному `path` (`LIKE 'prefix.%'`) и
точной привязке домов:

- **Нет улицы и дома** → прямой гибридный поиск объекта по терму.
- **Фаза 1 — контейнер.** Если назван регион/город, резолвим его лучший матч
  (`ResolveBestAsync`), берём его `path` как префикс поддерева.
- **Фаза 2a — дом.** Если назван дом: при известной улице резолвим её и ищем дома по
  `parent_object_id` (индекс-сик); иначе — по префиксу пути города. База номера матчится
  против `house_num`, корпус/строение — против `add_num1`/`add_num2` (мягкий бонус).
  Случай «улица+дом без города» (`Труда 11`, `Ленина 5`) → **многогородной поиск**: дом N
  по всем одноимённым улицам, крупные города первыми. Эта ветка пробуется **всегда**, когда
  есть имя и дом, но нет улицы — голое «имя + номер» почти всегда улица+дом. Раньше она
  включалась лишь когда лучший резолв имени сам оказывался улицей (level 8), но одноимённый
  НП глушил её (`Новый` → п. Новый из-за бонуса уровня, и дом искался по поддереву посёлка,
  возвращая дом N на чужой улице). Среди одноимённых улиц **точное** совпадение имени выше
  суперстрингов (`Набережная` над `Набережная Ветлужская`). Если многогородной поиск пуст
  (реально сельский дом прямо под НП, одноимённой улицы нет) — фолбэк на поддерево контейнера.
- **Фаза 2b — улицы.** Дома нет → перечисляем улицы в поддереве контейнера.

### Денормализованные фолбэки (homonym-proof)

Жёсткое сужение по `path` хрупко: контейнер-резолв (`ResolveBestAsync`) выбирает **один**
лучший матч, а одноимённых НП в области десятки (`Боровое` — 4 села) и имена бывают
многословными (`Верхний Уфалей`, `Большие Харлуши`). Промах резолва → префикс отсекает
эталон → пусто или дом N на чужой улице. Поэтому при неудаче основного пути идёт фолбэк по
**денормализованным** полям самой строки (`city`/`settlement`/`area` у улицы, `street` у дома) —
проверяется родной контейнер объекта, без сужения по дереву:

- **Улица (фаза 2b пуста).** `SearchStreetsByContainerAsync`: имя улицы по индексам
  `name_tsv`/`trgm`, контейнер — точным равенством денорм-полю. Граница «контейнер\|улица»
  перебирается по `NameTokens` в **обе стороны** (прямой порядок и reorder), берётся первый
  непустой результат. Чинит и гомонимы, и многословные НП, и обратный порядок.
- **Дом (точная привязка к улице не дала дома).** `SearchHousesByContainerStreetAsync`: номер по
  индексу `house_num`, имя улицы + контейнер — точным равенством денорм-полям дома. Иначе слепой
  поиск по поддереву вернул бы дом N на ЛЮБОЙ улице (`Березовка Мичурина 9` → ул. Центральная д9).

Оба фолбэка homonym-proof и срабатывают только когда основной путь промахнулся → 0 регрессий.
Денормализация `path`, `full_name`, реквизитов и решает проблему медленных JOIN при десятках
млн домов. Все `ORDER BY` имеют финальным тай-брейком `object_id` — выдача детерминирована
(иначе равные `Score`+`house_count` у дублей плавали между прогонами, зашумляя eval).

## 4. Recall-фолбэк (`AddressSearchService`)

Если основной разбор дал **пустую** выдачу, пробуются альтернативные интерпретации
(`AddressNormalizer.AlternativeSplits`) по очереди до первого непустого результата —
срабатывает только на нуле, поэтому не может ухудшить уже находимые запросы:

- тип-маркер как имя улицы (`Челябинск Тупик`; `город Линия 5` = дом 5 на ул. Линия);
- одиночный тип-маркер с домом без города (`Набережная 5`, `Линия 5`): имя улицы = маркер,
  дом сохраняем → многогородной поиск (иначе слово ушло бы в тип и поиск выдал бы пустые улицы);
- имя улицы вида «маркер + число» (`Линия 2`, `квартал 4`), когда число ошибочно ушло в дом;
- обратный порядок «улица … город» (`Ленина Магнитогорск`).

## 5. Адаптивный порог триграмм

У коротких имён одна перестановка букв роняет `similarity` ниже 0.3 (`леинна`/`ленина` =
0.27) — для терминов ≤ 6 символов порог опускается до 0.25, длинные остаются на 0.3
(меньше шума). Берётся минимальная длина среди значимых терминов (улица/город). Очень
короткие (`мриа`/`мира` = 0.11) триграммами всё равно не вытащить — глубже не идём.

## 6. Оценка качества (`Fias.Eval`)

«Золотой набор» генерируется прямо из `search.*`: каждая строка уже несёт эталонный
`object_guid`, регион и денормализованные город/улица/тип — запрос синтезируется, а
правильный ответ известен без ручной разметки. Выборка детерминирована
(`md5(object_id || seed)`), бакеты: `clean`, `reorder`, `typo`, `abbrev`, `house`,
`nocity`, `type`. Метрики — `recall@1/5/10` и `MRR` по бакетам и суммарно.

```bash
dotnet run --project Fias.Eval -- --region-count 5 --out eval-misses.csv
dotnet run --project Fias.Eval -- --query "Б.Хмельницкого 2"   # ad-hoc разбор кейса
```

Промахи (эталон не на #1 или вне выдачи) выгружаются в CSV для ручного разбора.

## Индексы проекции

| Индекс | Назначение |
|---|---|
| `GIN(name_tsv)` | полнотекстовый матч `@@` |
| `GiST(name gist_trgm_ops)` | нечёткий поиск + KNN по триграммам |
| `GIN(house_num gin_trgm_ops)` | номера домов |
| B-tree `path text_pattern_ops` | сужение по поддереву (`LIKE 'prefix.%'`) |
| B-tree `parent_object_id` | дома по родителю-улице (индекс-сик) |
| B-tree `object_guid`, `region_object_id` | резолв по GUID, фильтр по субъекту |

Эталонный SQL ранжирования и схема индексов — в [sql/hybrid_search.sql](sql/hybrid_search.sql).
